# Rubric — SC 2.4.3 Focus Order (Level A)

> Provenance: authored 2026-07-13 from the W3C *Understanding SC 2.4.3* document
> (WCAG 2.1). VPAT/auditor findings were quarantined from authorship.

## 1. Normative text

> **2.4.3 Focus Order** — If a Web page can be navigated sequentially and the
> navigation sequences affect meaning or operation, focusable components receive
> focus in an order that preserves meaning and operability.
>
> **Level A.**

Understanding doc: focus order "need not match visual layout precisely, provided it
remains logically coherent." The test is **preserved meaning and operability**, not
visual/DOM-order fidelity. F44 (tabindex order that breaks meaning/operability) and
F85 (dialog/menu not adjacent to its trigger in the sequence) are the named failures.

## 2. What the evidence looks like

- **`tabOrder` / walkTabOrder JSON** — the sequential list of `stops[]`, each with
  `role`, accessible `name`, `coords` (bounding box), `landmarkPath`,
  `followsPrevious` (boolean: is this stop after the previous one in **DOM order**?),
  and `wrap` (did focus cycle back to the start?).
- **Full-page screenshot with numbered focus badges** — each stop's ordinal drawn on
  the element, so you can see the *spatial* path the keyboard takes.

**How to read `followsPrevious`:** `false` marks a **DOM-order regression** — tab
went to an element that precedes the previous one in source. This is a **flag, not a
verdict.** Cross-check against the numbered-badge screenshot: DOM-backwards is NOT
automatically a failure. Focus can legitimately jump backward visually/DOM-wise and
still preserve meaning (e.g. a well-managed dialog, a toolbar, a skip link, a
grid). The question is whether a *user* would find the resulting order coherent and
operable.

## 3. Decision procedure (walk in order)

1. **Is sequential navigation meaningful here?** If the page has an ordered flow
   (form, wizard, reading + controls), the SC engages. Almost always yes for app
   pages.
2. **Trace the numbered badges spatially.** Does focus move in a coherent path
   (generally top→bottom, following the reading/logical grouping)? Minor
   left/right or grouped detours that mirror the visual structure are fine.
3. **Inspect each `followsPrevious === false`:**
   - Backward jump that still lands somewhere logical (into a just-opened dialog,
     back to a group header, along a toolbar/grid) → not a failure by itself.
   - Backward jump that strands the user, skips required fields, or scrambles the
     form order so operation breaks → **fail** (F44-style).
4. **Dialog/menu/popover adjacency (F85):** when a trigger opens an overlay, does
   focus move into (or the next tab reach) the overlay content, rather than
   continuing into the page *behind* it? If the overlay is inserted far from its
   trigger in the sequence and focus doesn't go there → **fail**.
5. **Keyboard traps / dead ends:** if `wrap` never occurs and focus escapes into
   browser chrome mid-page while content remains, or focus gets stuck → that's more
   2.1.1/2.1.2, but a broken *order* that prevents reaching a control → **fail** on
   operability grounds.
6. **Offscreen/hidden-but-focusable stops:** a badge with coords far offscreen or on
   a `display` that should be hidden, receiving focus in the middle of the flow →
   likely **fail** (focus goes to invisible content, breaking operability), or
   `needs_human` if you can't tell it's truly hidden.
7. If the only issue is DOM-backwards jumps that *might* be fine depending on live
   AT/reading experience → **needs_human**.

**Confidence:** `high` when badge path + JSON agree and the flow is a standard form;
`low` when the page is a complex composite widget (grid/tree/editor) whose expected
order isn't obvious → lean `needs_human`.

## 4. Pass exemplars

- **Clean top-to-bottom form.** All `followsPrevious === true`; badges descend the
  page in reading order; `wrap` returns to the first control. PASS, confidence high.
- **Managed dialog (legitimate backward jump).** Trigger is badge 5; opening it
  moves focus to the dialog's first control (badge 6) which sits visually centered;
  `followsPrevious` may be `false` because the dialog is appended at end of DOM, but
  the badge path shows focus correctly entering the dialog and the next stops stay
  inside it. PASS — meaning/operability preserved despite DOM-backwards flag.
- **Toolbar / radiogroup arrow-key composite.** A Chakra/Zag segmented control
  exposes a single tab stop then arrow-key navigation; `tabOrder` shows one stop,
  badges land on it once. PASS — roving-tabindex is a conforming pattern, not a
  skipped-control failure.
- **Third-party nuance.** Monaco editor is a single tab stop (the textbox); tabbing
  past it continues to the next page control. PASS — unconventional but operable.

## 5. Fail exemplars

- **tabindex scramble (F44).** Positive `tabindex` values force the order
  4→1→3→2 across form fields; badges zig-zag and a required field is reached only
  after the submit button. FAIL, severity 4 — operation broken.
- **Focus behind modal.** A dialog opens but the next several tab stops (badges)
  land on page content *behind* the overlay (the trigger region, nav), never
  entering the dialog; `followsPrevious` true but spatially the path leaves the
  dialog. FAIL, severity 4 (F85).
- **Skip past required control.** Badge sequence jumps from a field to the submit
  button, skipping an intermediate required input entirely (no badge on it, and it
  is keyboard-focusable per the DOM). FAIL, severity 4.
- **Offscreen detour.** Badge 7 sits at coords (-9999, y) — focus goes to a
  visually-hidden but still-focusable menu mid-flow, disorienting keyboard users.
  FAIL, severity 3.

Third-party-widget caution: roving tabindex, arrow-key grids/menus, and
end-of-DOM-appended dialogs routinely produce `followsPrevious === false` yet fully
conform. Fail only when meaning or operability is actually broken (a control can't
be reached in a sensible order, or focus is stranded), not for DOM-order novelty.

## 6. needs_human triggers

- DOM-backwards jumps whose acceptability depends on the live AT reading experience
  or on how a composite widget is *meant* to be operated.
- Complex custom widgets (trees, grids, editors) where the "correct" order is
  domain-specific and not inferable from badges alone.
- Whether an offscreen/low-opacity stop is genuinely hidden (should be skipped) vs.
  intentionally reachable.
- Dynamic insertion (content added after a trigger) where the sequence at capture
  time may differ from runtime timing.

## 7. Known evidence limits

- `tabOrder` captures Tab/Shift+Tab sequential focus only — it does **not** exercise
  arrow-key/Home/End intra-widget navigation, so a composite widget's *internal*
  order is invisible. → request `arrowKeyTraceForWidget`.
- The trace is a snapshot; focus order that changes as dynamic content
  appears/disappears (async dialogs, lazy panels) may not be fully represented. →
  request `postInteractionTabTrace`.
- `followsPrevious` is DOM-order, not visual-order; the badge screenshot supplies
  the visual read but a single screenshot can't show reading order for AT.
- No detection of *whether* an element is perceivably hidden beyond coords/opacity
  heuristics; true visibility needs computed style you may not have.

## 8. Severity guidance

- **5** — focus order makes it impossible to complete the primary task by keyboard
  (required control unreachable, or focus permanently stranded).
- **4** — operation broken for a key flow: fields skipped, focus behind modal,
  positive-tabindex scramble across a form.
- **3** — disorienting but recoverable: offscreen detour, one awkward backward jump
  that costs the user effort.
- **2** — minor order oddity that doesn't impede completion.
- **1** — cosmetic: order differs from ideal but fully coherent.
