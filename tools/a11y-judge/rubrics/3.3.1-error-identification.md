# Rubric — SC 3.3.1 Error Identification (Level A)

> Provenance: authored 2026-07-13 from the W3C _Understanding SC 3.3.1_ document
> (WCAG 2.1). VPAT/auditor findings were quarantined from authorship.

## 1. Normative text

> **3.3.1 Error Identification** — If an input error is automatically detected, the
> item that is in error is identified and the error is described to the user in text.
>
> **Level A.**

Understanding doc — three required elements once an error is auto-detected:

1. the fact that "an error has occurred" is conveyed,
2. "the item that is in error is identified," and
3. "the error … [is] described to the user in text."

"Re-displaying a failed form without explanation is insufficient." Descriptions
should state the problem and ideally how to fix it. Named failure family: relying on
color/icon **only** (no text), and generic rather than specific messages.

## 2. What the evidence looks like

- **`errorFlows` transcript** — the scripted flow: what was entered/submitted, and
  the resulting state. Confirms an error was actually _detected_ (so the SC engages).
- **Post-error DOM dump** — per field: `aria-invalid`, `aria-describedby` (and the
  text it points to), associated error-message text/nodes, and any `role="alert"` /
  live-region content that fired.
- **`liveRegions` log** — whether an alert/status announced the error and with what
  text.
- **Post-error screenshot** — the visual error state (red borders, icons, message
  placement) to compare against what's exposed in text/programmatically.

**Core judgment:** when validation fails, is the erroring item **identified** and is
the error **described in text** (not by color/icon alone), and is that description
**specific** enough to know what's wrong? The programmatic exposure
(`aria-invalid`/`describedby`/alert) determines whether non-visual users get it too.

## 3. Decision procedure (walk in order)

1. **Did an input error get auto-detected?** From the transcript: if the form
   rejected input / blocked submit / flagged a field. If no error is detectable in
   the flow, the SC is **not engaged** → report `needs_human`/insufficient rather
   than pass, and note the collector should force an error.
2. **Is the error described in TEXT?** There must be human-readable text stating an
   error occurred. Color/border/icon _only_ (no text) → **fail**.
3. **Is the item in error identified?** The text must make clear _which_ field/input
   is wrong — via message adjacency + programmatic association
   (`aria-describedby` → the message, or the message names the field). A single
   generic "There were errors" with no field identification → **fail** (item not
   identified).
4. **Is the description specific?** "Invalid input" / "Error" is weak; "Email must
   contain @" or "Enter a date in MM/DD/YYYY" is adequate. Generic-only → **fail**
   (or severity-graded partial fail; see §8). Understanding doc calls generic
   messages a failure scenario.
5. **Is it exposed to AT?** Check `aria-invalid="true"` on the field AND that the
   message is programmatically linked (`aria-describedby`) or announced
   (`role="alert"`/live region with the text). Visually-only text that is not
   associated/announced → **fail** for non-visual users (severity depends on
   whether visual users are served).
   - Note: _announcing_ on error overlaps SC 4.1.3; the _description in text_
     obligation is 3.3.1. Judge 3.3.1 on identification+description; cross-cite 4.1.3
     if the announcement mechanism is the gap.
6. **Roll-up:** `pass` only if all detected errors are identified AND described in
   specific text AND that text is programmatically available. `needs_human` if you
   can't tell whether the error was actually triggered, or whether the association is
   correct.

**Confidence:** `high` when transcript shows a clear error and the dump shows the
message + association; `low` when it's unclear an error fired.

## 4. Pass exemplars

- **Field-level, associated, specific.** Transcript: submitted empty required email.
  Dump: the email input has `aria-invalid="true"` and `aria-describedby` → a message
  node reading "Email address is required." Screenshot shows the same text under the
  field. PASS.
- **Format guidance.** Bad date entry yields text "Enter the date as MM/DD/YYYY",
  associated via `describedby`, `aria-invalid` set. PASS — describes problem + fix.
- **Summary + per-field.** An error summary lists "2 problems" with links, and each
  field also has an associated, specific message and `aria-invalid`. PASS.
- **Third-party nuance.** SurveyJS marks a skipped required question with
  `aria-invalid` and a linked "Response required" text; even though the widget's DOM
  is unconventional, the item is identified and described in text. PASS.

## 5. Fail exemplars

- **Color-only (no text).** Field border turns red, no text message anywhere; dump
  shows no error text, no `describedby`. FAIL, severity 4 — error conveyed by color
  alone.
- **Generic banner, item not identified.** A top banner "Submission failed. Please
  fix errors." with no indication of which field(s); no `aria-invalid` on any input.
  FAIL, severity 4 — item not identified, description not specific.
- **Visual-only text (not exposed).** A message renders visually beside the field
  but is not linked via `describedby` and no `aria-invalid`/alert; AT users get
  nothing. FAIL, severity 3–4 (visual users served, non-visual users not).
- **Silent re-display.** Form reloads with the bad values and no message at all
  ("re-displaying a failed form without explanation is insufficient"). FAIL,
  severity 4.

Third-party-widget caution: an unconventional error presentation (inline chip, tooltip)
passes if the erroring item is identified and the error is described in associated
text. Fail only when text is absent, generic, or the item isn't identified — not for
presentation style.

## 6. needs_human triggers

- The transcript does not clearly show an error was **detected** (SC may not be
  engaged; or the collector didn't trigger validation) — can't pass or fail.
- Whether a message is _specific enough_ is a judgment about user comprehension in a
  domain-specific form.
- The message text is dynamic/deferred (appears after async server validation) and
  the capture may have missed it. → often pairs with `evidenceGaps`.
- Correctness of the `aria-describedby` target (does it point to the _right_ message
  for _that_ field?) is ambiguous from the dump.

## 7. Known evidence limits

- Static capture may miss **async/server-side** errors that render after a delay. →
  request `postSubmitDelayedDump`.
- The probe exercises a _scripted_ set of invalid inputs; error paths the script
  didn't trigger are uncovered. → request `additionalErrorScenarios`.
- No live screen-reader: whether an `alert`/`describedby` is _actually announced_ is
  proxied by role/markup, not observed. (4.1.3 territory too.)
- Cannot judge whether a specific message is _correct_ domain guidance (e.g. a
  password-policy message that misstates the rule).

## 8. Severity guidance

- **5** — error blocks task completion and gives the user no way to know what to fix
  (silent failure on a required submission).
- **4** — error conveyed by color/icon only, or item unidentified, or not exposed to
  AT: affected users cannot recover.
- **3** — text present but generic, or visible-only (not programmatically
  associated): recovery is possible but hindered.
- **2** — minor: message slightly vague but the field is clearly identified.
- **1** — cosmetic wording of an otherwise clear, associated, specific error.
