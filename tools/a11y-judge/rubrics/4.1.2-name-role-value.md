# Rubric — SC 4.1.2 Name, Role, Value (Level A)

> Provenance: authored 2026-07-13 from the W3C _Understanding SC 4.1.2_ document
> (WCAG 2.1). VPAT/auditor findings were quarantined from authorship.

## 1. Normative text

> **4.1.2 Name, Role, Value** — For all user interface components (including but not
> limited to: form elements, links and components generated by scripts), the name
> and role can be programmatically determined; states, properties, and values that
> can be set by the user can be programmatically set; and notification of changes to
> these items is available to user agents, including assistive technologies.
>
> **Level A.**

Named failures: **F59** (script makes a div/span a control with no role), **F15**
(custom control not using the accessibility API), **F68** (control lacking a
programmatically determined name), **F79** (focus state not programmatically
determinable), **F86** (multi-part fields lacking individual names), **F89**
(image-only link with no accessible name), **F20** (name/value not updated on change).

### Scope of THIS judge

axe already catches many _missing_ names/roles (`button-name`, `link-name`,
`aria-*` validity). This rubric focuses on the judgment layer: **name that is
present but wrong/duplicated/uninformative**, **role that misrepresents the
control's function**, and **state/value that doesn't reflect reality** — the things
that are "technically named" yet fail equivalence.

## 2. What the evidence looks like

- **`nameRoleValue` per-control dump** — for each interactive component: `tag`,
  computed `role`, computed `accessibleName` (+ its source), and exposed
  `states/properties` (`aria-expanded`, `aria-checked`, `aria-selected`,
  `aria-pressed`, `disabled`, `value`, `aria-invalid`, etc.). Empty names are flagged.
- **`ariaSnapshot()`** — the accessibility tree: roles + names + states as AT sees
  them; good for spotting duplicated/echoed names ("button button") and
  missing/incorrect roles.
- **Icon/control crop** — the rendered control, so you can judge whether the exposed
  name/role/state matches the _actual_ visible function/state.

**Core judgment:** does each control expose (a) a **correct, meaningful name**,
(b) a **role matching its real function**, and (c) **states/values that reflect its
current condition**? Presence alone is not enough — a checkbox stuck at
`aria-checked="false"` while visibly checked fails on _value_.

## 3. Decision procedure (walk in order)

1. **Role vs. function:** compare computed `role` to what the crop shows the control
   does. A clickable `<div>` with no role (F59), or `role="button"` on something
   that is actually a checkbox/tab, → **fail** (role misrepresents).
2. **Name presence & quality:**
   - Empty/flagged name on an interactive control (F68/F89: icon-only button/link) →
     **fail**.
   - Name present but **wrong** (doesn't describe the control's purpose/target;
     e.g. accName "Submit" on a Cancel button) → **fail**. (Cross-cite 2.4.6.)
   - Name **duplicated/echoed** ("button button", label text repeated in aria-label
     - visible text so AT says it twice, or the role word baked into the name) →
       **fail** or severity-graded finding depending on impact.
   - Name **generic** where a specific one is needed ("link", "button", "click
     here" with no context) → **fail**/finding.
3. **States & properties:** for toggles/expanders/selections, does the exposed state
   match the crop? `aria-expanded` present and correct on a disclosure; `aria-checked`
   tracks the visible check; `aria-selected` on the active tab; `disabled`/
   `aria-disabled` on a greyed control. Missing or **stale/incorrect** state (F79 for
   focus, F20 for un-updated value) → **fail**.
4. **Value:** editable/selectable components expose their current value
   (`value`, `aria-valuenow`, selected option). Missing/incorrect → **fail**.
5. **Multi-part fields (F86):** split inputs (e.g. phone as 3 boxes, a date as 3
   selects) each need an individual accessible name → else **fail**.
6. **Roll-up:** `pass` only when name (correct + meaningful), role (accurate), and
   state/value (current) all hold for the controls in scope. `needs_human` when
   correctness of a name/role hinges on intended semantics you can't infer, or when
   dynamic state-change notification can't be observed statically.

**Confidence:** `high` when dump + crop agree and the control is standard; `med` for
custom composites; `low` (→ needs_human) when intended role/semantics is unclear.

## 4. Pass exemplars

- **Standard control, clean triple.** `<button>` accName "Submit assignment",
  role button, not disabled; crop matches. PASS.
- **Custom toggle done right.** A Chakra/Zag Switch exposes `role="switch"`,
  accName "Email notifications", `aria-checked` tracking the visible thumb position.
  PASS — custom but complete name/role/value.
- **Disclosure with live state.** An accordion header: `role="button"`,
  `aria-expanded` flips true/false matching the crop's open/closed chevron. PASS.
- **Third-party nuance.** Monaco's editor surface exposes `role="textbox"` with an
  accessible name and its text value; unconventional internals but the triple is
  present and correct. PASS.

## 5. Fail exemplars

- **Div-as-button, no role (F59).** Dump: `tag=div`, `role` empty, has a click
  handler; crop shows a button. FAIL, severity 4 — AT can't identify or operate it.
- **Icon-only, no name (F68/F89).** A trash-icon delete button; accName empty
  (flagged). FAIL, severity 4 — user can't tell what it does. Suggested fix:
  `aria-label="Delete submission"`.
- **Echoed/duplicated name ("button button").** `ariaSnapshot` shows the button
  announced as "button button" (role word baked into the label). FAIL, severity 2–3
  — confusing/noisy, name not clean.
- **Wrong name.** A Cancel control accNamed "Submit". FAIL, severity 4 — actively
  misleads; user triggers the wrong action. Cross-cite 2.4.6.
- **Stale state (F20).** A visibly-checked custom checkbox still reports
  `aria-checked="false"` in the dump. FAIL, severity 4 — value doesn't match reality.
- **Missing expanded state.** A menu button with no `aria-expanded`; AT can't tell
  if the menu is open. FAIL, severity 3.

Third-party-widget caution: a widget using an _uncommon-but-valid_ role/pattern
(e.g. `role="combobox"` composite, roving tabindex) passes if name/role/value are
correctly exposed. Fail only on the SC's actual conditions — missing/wrong name,
wrong/absent role, or state/value not reflecting reality — not on style or novelty.

## 6. needs_human triggers

- **Change-notification** ("notification of changes … available to AT"): whether a
  dynamic value/state change is _actually announced_ can't be fully observed
  statically — the dump shows the attribute, not the live AT notification.
- Whether an unconventional custom role is the _semantically correct_ one for the
  intended interaction pattern (design-intent question).
- A name that is terse/ambiguous but _might_ be adequate in context (borderline with
  2.4.6).
- Composite widgets whose full state model (owns/controls/activedescendant chains)
  can't be validated from a flat dump.

## 7. Known evidence limits

- Static dump captures state **at capture time**; it cannot confirm that
  name/role/value **update and notify** on interaction (F20 dynamic case). →
  request `postInteractionStateDump` / `changeNotificationTrace`.
- No live AT: "available to user agents including AT" is proxied by ARIA/DOM
  correctness, not observed announcement.
- `owns`/`controls`/`activedescendant` relationship _correctness_ isn't fully
  validated by the accname/role dump. → request `relationshipGraph`.
- Crops may be too small to confirm the visible state a control is claiming.

## 8. Severity guidance

- **5** — a control essential to the task is unidentifiable/unoperable by AT
  (no role AND no name on the only submit path).
- **4** — missing/wrong name, wrong/absent role, or state/value contradicting
  reality on a functional control: user can't identify, operate, or trust it.
- **3** — missing non-critical state (e.g. `aria-expanded`), or name present but
  under-informative on a secondary control.
- **2** — echoed/noisy name; cosmetic role-word duplication.
- **1** — trivial naming nitpick with no operational impact.
