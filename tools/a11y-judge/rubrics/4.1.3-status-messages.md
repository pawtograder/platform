# Rubric — SC 4.1.3 Status Messages (Level AA)

> Provenance: authored 2026-07-13 from the W3C *Understanding SC 4.1.3* document
> (WCAG 2.1). VPAT/auditor findings were quarantined from authorship.

## 1. Normative text

> **4.1.3 Status Messages** — In content implemented using markup languages, status
> messages can be programmatically determined through role or properties such that
> they can be presented to the user by assistive technologies without receiving focus.
>
> **Level AA.**

Definition (Understanding doc): a **status message** "provides information to the
user on the success or results of an action, on the waiting state of an application,
on the progress of a process, or on the existence of errors," and is **not delivered
via a change in context** (it does not move focus/viewport/meaning). Four situations:
- **A:** success / results of an action / app state → `role="status"` (polite).
- **B:** errors / warnings / suggestions → `role="alert"` or live region.
- **C:** progress of a process → `role="log"` / `role="progressbar"` / live region.
- **D:** results/completion feedback.

Named failure **F103:** status messages that cannot be programmatically determined
through role or properties. Also: misusing `role="alert"`/`aria-live="assertive"`
for non-time-sensitive content.

## 2. What the evidence looks like

- **`liveRegions` mutation timeline** — a MutationObserver log of every
  `aria-live` / `role="status"` / `role="alert"` / `role="log"` region: its
  **politeness** (`polite`/`assertive`/`off`), and a timestamped list of text
  mutations. This tells you *whether a region existed AND carried the message text at
  the moment the status event happened*.
- **Screenshots at status changes** — the visible status (toast, inline "Saved",
  spinner, progress bar, error banner) so you can confirm a status *event actually
  occurred* and compare it to what the live-region log captured.
- **`errorFlows` transcript** (for situation B) — ties an error status to the action
  that produced it.

**Core judgment:** for each visible status change, was there a **programmatically
determinable** announcement — a live region / status / alert role that **contained
the message text at mutation time**, with **appropriate politeness**, and **without
moving focus**? The classic trap: a region that *exists* but is **empty** when the
status appears (text injected elsewhere, or the region created after the fact), or a
toast shown purely visually with no live region at all.

## 3. Decision procedure (walk in order)

1. **Identify each status event** from the screenshots/transcript: autosave "Saved",
   submit success, validation error surfaced without focus move, upload progress,
   "Loading…", results-ready. For each, the SC applies (it's a status message, not a
   change of context).
2. **Was it a change of context instead?** If the update moved focus / navigated /
   opened a dialog that takes focus, it's **out of scope** for 4.1.3 (handled by
   focus management / 4.1.2) — note and move on.
3. **Find the matching live-region mutation** in the timeline at ~the event's
   timestamp:
   - A region with an appropriate role (`status`/`alert`/`log`) or `aria-live`
     **whose text mutated to the message** at that time → the message is
     programmatically determinable → **pass** that event.
   - A region exists but its text was **empty / unchanged** at event time (message
     rendered only in a non-live node, e.g. a plain toast div) → **fail** (F103) —
     AT users get nothing.
   - **No** live region / status role at all for a visible status → **fail** (F103).
4. **Politeness appropriateness:**
   - Non-urgent status (save/progress/results) uses `polite`/`role="status"` → good.
   - Non-urgent status forced through `assertive`/`role="alert"` (interrupts the
     user repeatedly, e.g. an autosave toast every keystroke as an alert) → finding;
     misuse of assertive → **fail** or severity-graded (interrupts/annoys but is
     "determinable"). Use judgment: mild misuse = finding, disruptive misuse = fail.
   - Time-sensitive error using `polite` when it needs immediacy → usually a finding,
     not a hard fail, unless the delay defeats the purpose.
5. **Focus check:** confirm the status did **not** steal focus (a status message that
   receives focus violates the "without receiving focus" clause / is a context change).
6. **Live-region hygiene:** a region that is added to the DOM *with text already in
   it* (rather than being present-and-empty then updated) may not be announced by
   some AT — if the timeline shows the whole region node inserted with text (not a
   text mutation into an existing region) → **needs_human** (AT-dependent) or a
   low-confidence finding.
7. **Roll-up:** `pass` only if every in-scope status event was determinable via
   role/properties with text present and appropriate politeness, without taking
   focus. `fail` on any empty/absent live region for a real status. `needs_human`
   for announce-ability edge cases that depend on live AT behavior.

**Confidence:** `high` when the timeline clearly shows (or lacks) a text mutation in
a correctly-roled region at the event; `low` for insertion-vs-mutation edge cases →
needs_human.

## 4. Pass exemplars

- **Autosave polite status.** Screenshot shows "Saved". Timeline: an existing
  `role="status"` (`aria-live="polite"`) region present since load, text mutated
  from "" → "All changes saved" at the save timestamp, no focus change. PASS.
- **Error as alert (situation B).** A validation error surfaces without moving
  focus; timeline shows a `role="alert"` region receiving "Email is required" at the
  submit timestamp. PASS (appropriate assertive-class role for an error).
- **Progress via log/progressbar.** An upload shows a progressbar with
  `aria-valuenow` updating and/or a `role="log"` announcing "Uploading 50%". PASS.
- **Third-party nuance.** A Chakra toast that mounts a persistent
  `aria-live="polite"` container and injects the message text into it as a mutation.
  PASS — the mechanism is a real live region even though it's a toast.

## 5. Fail exemplars

- **Visual-only toast (F103).** Screenshot shows a "Submission received" toast;
  timeline shows **no** live region / status role and **no** aria-live mutation. FAIL,
  severity 4 — non-visual users never learn the action succeeded.
- **Empty live region.** A `role="status"` node exists but stays empty; the message
  text is rendered into a sibling plain `<div>`. Timeline: no text mutation inside
  the status region. FAIL, severity 4.
- **Late region insertion.** The message text and its `aria-live` region are inserted
  together *after* the event; many AT won't announce a region that arrives already
  populated. FAIL or needs_human depending on confidence (see §3.6).
- **Assertive misuse (disruptive).** Every keystroke's autosave fires a
  `role="alert"`, interrupting the screen reader continuously. FAIL, severity 3 —
  determinable but actively harmful; should be polite.

Third-party-widget caution: a widget's *unconventional* status UI (inline chip,
snackbar, custom progress) passes if a role/live-region carries the text
determinably without stealing focus. Fail only when the status is not
programmatically determinable, not for visual style.

## 6. needs_human triggers

- **Insertion vs. mutation** ambiguity: whether an AT will announce a region that was
  inserted already-populated is AT/version-dependent.
- Whether `polite` vs `assertive` is *appropriate* for a borderline-urgency message
  (a UX/severity judgment).
- A status that appears only after real async timing the capture may have missed
  (can't confirm the region ever got the text).
- Whether an update is truly a "status message" vs. a "change of context" when focus
  behavior is ambiguous in the capture.

## 7. Known evidence limits

- **No live screen reader:** the timeline proves the *markup/text* was present and
  polite, which is the SC's programmatic-determinability requirement — but actual
  announcement (and the insertion-vs-mutation nuance) is proxied, not observed. →
  request `screenReaderAnnouncementTrace`.
- Timing windows: a debounced/short-lived status may mutate and clear between capture
  frames; the MutationObserver log mitigates this but async server events can still
  be missed. → request `extendedObservationWindow`.
- The probe may not correlate *which* visible status maps to *which* region if
  multiple regions mutate near-simultaneously. → request `regionToEventMapping`.
- Cannot judge whether text is *meaningful* to a user beyond its presence (overlaps
  1.1.1/3.3.1 for wording quality).

## 8. Severity guidance

- **5** — critical outcome (submission accepted/rejected, payment, irreversible
  action) is announced only visually; non-visual users are left unaware of task
  result.
- **4** — routine but important status (save success, validation error, results
  ready) not programmatically determinable (empty/absent live region).
- **3** — determinable but wrong politeness that disrupts (assertive spam) or delays
  perception.
- **2** — minor: a low-importance status lacks announcement, or slight politeness
  mismatch.
- **1** — cosmetic: redundant or trivially-worded announcement.
