# Rubric — SC 2.4.7 Focus Visible (Level AA)

> Provenance: authored 2026-07-13 from the W3C _Understanding SC 2.4.7_ document
> (WCAG 2.1). VPAT/auditor findings were quarantined from authorship. WCAG 2.2
> SC 2.4.11 Focus Appearance is cited below only as _informative_ clarification;
> the normative bar here is 2.1 Level AA.

## 1. Normative text

> **2.4.7 Focus Visible** — Any keyboard operable user interface has a mode of
> operation where the keyboard focus indicator is visible.
>
> **Level AA.**

Understanding doc: the indicator "must not be time limited — when the keyboard focus
is shown it must remain." Authors need at least **one mode** where focus is visible.
Named failures: **F55** (script removes focus when element receives it) and **F78**
(styling outline/border so the visual focus indicator is removed or non-visible).

_Informative (WCAG 2.2 SC 2.4.11):_ an indicator is stronger when it is at least as
large as a 2px-thick perimeter of the component and has ≥3:1 contrast against
adjacent colors between focused/unfocused states. Use this as a _quality_ heuristic;
do not fail 2.4.7 solely for missing the 2.2 numeric thresholds — but a change so
faint it is effectively invisible does fail 2.4.7 (F78).

## 2. What the evidence looks like

- **`focusIndicator` per-stop computed style — measured WHILE focus is held live.**
  For each focusable stop: computed `outline` (style/width/color), `boxShadow`,
  `border`, `backgroundColor`, and any indicator-related properties, captured at the
  moment keyboard focus is on the element (never after blur).
  > **Zag/Chakra gotcha:** `data-focus-visible` is applied by an async React
  > re-render, so blur/refocus style-_diffing_ false-negatives. The probe measures
  > computed style while focus is live; trust the live measurement, not a diff.
- **Screenshot pair per stop:** (a) the live _focused_ crop, and (b) the same
  rectangle from the pristine pre-tab screenshot (the unfocused baseline). Compare
  the two crops to see whether a visible change actually renders.

**Read the pair, not just the numbers.** The computed style tells you _what_ is
declared; the crop pair tells you whether it is _perceivable_. `outline: none` with
a compensating `box-shadow` still passes if the crop shows a clear ring.

## 3. Decision procedure (walk in order)

1. **Is the element keyboard-operable?** Non-interactive text stops with no focus
   are out of scope. Every interactive stop needs a visible focus indicator.
2. **Read the computed style for a declared indicator:** a non-`none` `outline`, a
   focus `box-shadow`, a border change, or a background/color change bound to focus.
3. **Confirm perceivability from the crop pair:**
   - Focused crop shows a clear, distinguishable change vs. the pristine crop
     (ring, outline, halo, border, obvious background shift) → **pass** that stop.
   - Computed style declares an indicator AND the crop confirms it renders → pass.
   - `outline: none`/`outline: 0` (or width 0) AND no other indicator in the crop
     (crop looks identical focused vs. pristine) → **fail** (F78).
   - Indicator present but so subtle it may not be perceivable (a faint background
     tint only) → judge from the crop; if you cannot tell whether the change clears
     a "clearly visible" bar without pixel-contrast data → **needs_human**.
4. **Time-limited indicators:** if evidence shows the indicator appears then
   disappears while focus remains (rare in static capture; look for animations noted
   in metadata) → **fail**.
5. **Roll-up:** `fail` if any interactive stop has no visible indicator; `pass` if
   every stop shows one; `needs_human` if the only questionable stops are
   subtle-contrast cases you can't adjudicate from the crops.

**Confidence:** `high` when crop pairs clearly show/omit an indicator; `med` when
relying on computed style with a small crop; `low` (→ needs_human) for subtle
contrast-dependent cases.

## 4. Pass exemplars

- **Standard outline.** Computed `outline: 2px solid …`; focused crop shows a clear
  ring absent in the pristine crop. PASS, confidence high.
- **box-shadow ring (outline:none but compensated).** Computed `outline: none` but
  `box-shadow: 0 0 0 3px …`; crop pair shows an obvious halo. PASS — F78 is about
  _removing_ the indicator, and here a clear one exists.
- **Chakra Switch / Zag control.** Live-measured computed style shows a focus ring
  token applied; focused crop shows the ring. PASS — the live measurement sidesteps
  the async `data-focus-visible` diff false-negative.
- **Background + border shift.** Button focus flips to a darker fill _and_ a border;
  crop pair shows a strong, unmistakable change. PASS.

## 5. Fail exemplars

- **Outline removed, nothing else (F78).** Computed `outline: none`; focused crop is
  pixel-identical to pristine; no box-shadow/border/background change. FAIL,
  severity 4 — keyboard users cannot see focus location.
- **Script steals focus indicator (F55).** Metadata/transcript shows focus is
  programmatically blurred or a `mousedown` handler removes the focus class on
  keyboard focus; crop shows no indicator. FAIL, severity 4.
- **Only a subtle background nudge that the crop shows is imperceptible.** Focused
  crop differs from pristine by a barely-there tint that is effectively invisible.
  FAIL, severity 3 — but if borderline, prefer needs_human (see triggers).
- **Custom widget hides native focus.** A third-party control sets `outline:none` on
  its focusable inner element and provides no replacement; crop confirms no
  indicator. FAIL, severity 4.

Third-party-widget caution: an _unconventional_ indicator (e.g. an inset glow, a
color inversion, an animated underline) passes if the crop shows it is clearly
perceivable. Do not fail a widget for using a non-outline indicator; fail only when
_no_ perceivable indicator exists or it is effectively invisible.

## 6. needs_human triggers

- The only indicator is a **subtle background/color change** whose sufficiency
  depends on contrast the crops don't let you measure confidently (no pixel-contrast
  probe).
- The only visible focus cue is a **text-caret in a text field** — a blinking caret
  may or may not satisfy "focus indicator" for that control depending on
  interpretation; route to human.
- Indicator relies on animation/transition whose persistence can't be confirmed from
  a static crop.
- Crop is missing, mis-registered (focused vs. pristine rects don't align), or
  downscaled below the point where a thin ring is discernible.

## 7. Known evidence limits

- **No pixel-level contrast measurement** between indicator and adjacent colors —
  the 2.2/2.4.11 ≥3:1 heuristic can't be computed; borderline contrast → needs_human.
  → request `focusIndicatorContrastRatio`.
- Static crops can't show **temporal** behavior (indicator that fades/disappears) or
  animation. → request `focusHoldVideo` or `postDelayCrop`.
- Crops are downscaled (≤1000px long edge per bundle writer); a 1–2px ring may be
  hard to see. → request `fullResFocusCrop`.
- The live-measure probe covers Tab-reachable stops; intra-widget arrow-key focus
  states may not be sampled. → request `arrowKeyFocusCrops`.
- Caret-only fields: the probe reports computed style but the caret itself may not be
  in the crop.

## 8. Severity guidance

- **5** — no visible focus anywhere on a keyboard-only critical flow: the user
  cannot operate the page at all without sight of focus.
- **4** — a key interactive control (submit, primary nav, form field) has no
  perceivable focus indicator.
- **3** — indicator present but weak/subtle on important controls; usability harmed.
- **2** — minor: indicator slightly inconsistent or weak on secondary controls.
- **1** — cosmetic difference from an ideal indicator; clearly visible regardless.
