# Rubric — SC 2.4.6 Headings and Labels (Level AA)

> Provenance: authored 2026-07-13 from the W3C *Understanding SC 2.4.6* document
> (WCAG 2.1). VPAT/auditor findings were quarantined from authorship.

## 1. Normative text

> **2.4.6 Headings and Labels** — Headings and labels describe topic or purpose.
>
> **Level AA.**

Understanding doc key points:
- Applies to headings and labels **when present** — it does not *require* them
  (that presence question is 1.3.1 / 3.3.2 / 2.4.1 territory). This SC is about
  **descriptiveness**.
- "A word, or even a single character, may suffice if it provides an appropriate
  cue" — brevity is fine; descriptiveness ≠ length.
- Uniqueness is **not** required, but ambiguous duplicate labels can fail if they
  don't distinguish purpose.
- "Headings and labels must be programmatically determined, per SC 1.3.1."

## 2. What the evidence looks like

- **`readingOrder` heading outline** — the `h1…h6`/`role="heading"` text in document
  order with levels, i.e. the section titles a user scans.
- **`nameRoleValue` / accessible-name dump** — form controls and their label text
  (visible `<label>`, `aria-label`, `aria-labelledby`, `title`).
- **Full-page screenshot** — the visual context each heading/label sits in, needed
  to judge whether the text actually describes *that* section/control.

The judgment: **does each heading describe its section's topic, and each label
describe its control's purpose?** Compare the text against what the section/control
actually is (from the screenshot + surrounding content). Vague, boilerplate,
copy-paste, or mismatched text fails.

## 3. Decision procedure (walk in order)

1. **Headings:** for each heading, read its text against the content beneath it.
   - Describes the topic (even briefly) → pass this heading.
   - Generic placeholder ("Section", "Untitled", "Heading 1"), or text that
     describes a *different* section than it heads → contributes to **fail**.
   - Multiple headings with identical text where the sections differ in purpose and
     nothing distinguishes them → **fail** (ambiguous), *unless* context makes the
     purpose obvious.
2. **Labels:** for each labeled control, read the label/accName against the
   control's function (from screenshot + role).
   - Describes purpose ("Email address", "Search", even an icon-only "Search") →
     pass this control.
   - Placeholder-as-label only, or a label that misdescribes the control, or a
     duplicated label that doesn't distinguish two controls with different purposes
     (e.g. two "Edit" buttons with no context) → **fail**.
   - Note: a *present but wrong* accName (e.g. "Submit" on a Cancel button) fails
     both here (not descriptive) and 4.1.2 (name) — cite both.
3. **Verdict roll-up:** `pass` if all headings/labels present are adequately
   descriptive; `fail` if any material heading/label is non-descriptive/misleading
   in a way that impairs orientation or control identification; `needs_human` if
   descriptiveness hinges on domain meaning you can't judge.

Note the boundary: **absence** of a needed heading/label is not this SC. If a
control has *no* name at all, that's 4.1.2/3.3.2 — flag it but don't fail 2.4.6 for
absence; 2.4.6 judges the quality of what is present.

**Confidence:** `high` when screenshot + text make topic/purpose clear; `low` when
domain jargon makes "descriptive" a subjective call → `needs_human`.

## 4. Pass exemplars

- **Concise but descriptive heading.** Section listing due assignments is headed
  "Upcoming Deadlines"; content matches. PASS.
- **Single-word label with clear cue.** A search field labeled "Search"; an
  icon-only search button whose accName is "Search". PASS — brevity is fine.
- **Non-unique but disambiguated.** Several "Download" links, each inside a row that
  names the file (visible context / `aria-labelledby` combining row + action). PASS
  — uniqueness not required; purpose is distinguishable.
- **Third-party nuance.** A SurveyJS page groups questions under headings generated
  from the question titles; headings read as the actual question topics. PASS even
  though the heading markup is widget-generated.

## 5. Fail exemplars

- **Placeholder heading.** A panel headed "Section 2" (or "Lorem ipsum") over grade
  content. FAIL, severity 3 — gives no orientation cue.
- **Mismatched heading.** Heading reads "Announcements" but the section below is a
  file-upload form. FAIL, severity 3 — misleads scanning users.
- **Ambiguous duplicate labels.** Two adjacent buttons both accNamed "Edit" with no
  distinguishing context, controlling different items. FAIL, severity 3 — user
  can't tell which edits what.
- **Placeholder-as-label.** An input whose only "label" is grey placeholder text
  "Enter value" (disappears on focus, not a programmatic label). FAIL, severity 3
  (also touches 1.3.1/4.1.2).

Third-party-widget caution: an unconventional label *format* (e.g. a compound
"Question 3 of 10 — Rate your experience") is not a failure — it is descriptive.
Fail only when the text genuinely fails to convey topic/purpose.

## 6. needs_human triggers

- Descriptiveness depends on domain knowledge (discipline jargon, course-specific
  terms) you cannot evaluate as adequate.
- Duplicate labels where whether context "obviously" disambiguates is a judgment
  about real user comprehension.
- A heading/label that is terse and *might* be an appropriate cue for the target
  audience but reads cryptic to a generalist.
- Whether text is a true programmatic label vs. adjacent decorative text — if the
  accName source is unclear from the dump.

## 7. Known evidence limits

- The dump gives the *computed* accName but the screenshot may not reveal whether a
  visually-adjacent word is programmatically associated — association correctness is
  partly 1.3.1.
- Heading *level* correctness (skipped levels, structure) is 1.3.1, not judged here;
  this rubric judges heading text quality only.
- No audience/domain lexicon: "descriptive to whom" can't be resolved statically for
  specialist content.
- Placeholder text captured as an accName source may or may not persist on focus;
  the static dump can't show the disappear-on-focus behavior. → request
  `labelPersistenceOnFocus`.

## 8. Severity guidance

- **5** — rare: a mislabeled control causes a destructive/irreversible wrong action
  (e.g. "Save" that actually deletes).
- **4** — labels so non-descriptive/ambiguous that the user cannot determine a
  control's purpose needed to complete the task.
- **3** — non-descriptive or misleading heading/label that impairs orientation but
  is recoverable via context.
- **2** — mildly vague heading/label; minor orientation cost.
- **1** — cosmetic wording nitpick with no real impact.
