# Rubric — SC 1.3.2 Meaningful Sequence (Level A)

> Provenance: authored 2026-07-13 from the W3C *Understanding SC 1.3.2* document
> (WCAG 2.1). VPAT/auditor findings were quarantined from authorship.

## 1. Normative text

> **1.3.2 Meaningful Sequence** — When the sequence in which content is presented
> affects its meaning, a correct reading sequence can be programmatically determined.
>
> **Level A.**

Key nuance from the Understanding doc: the SC applies **only when sequence affects
meaning**. "The relative order of the main section of a web page and a navigation
section does not affect their meaning." And "there may be more than one order that
is 'correct'" — only *one* correct programmatic sequence must exist.

## 2. What the evidence looks like

- **`readingOrder` DOM-order text serialization** — the content flattened in DOM
  order, with headings/roles/list markers annotated. This is the *programmatically
  determined* sequence a screen reader follows.
- **`ariaSnapshot()`** — the accessibility-tree order (usually tracks DOM order),
  useful to confirm nesting/labels.
- **Survey-specific probe** — question text vs. its answer-options order (SurveyJS
  is a known reorder risk).
- **Full-page screenshot (visual order)** — the sighted reading order.

**The core judgment is: does the DOM/reading order match the visual/logical order
*where order carries meaning*?** A disagreement between the screenshot and the
serialization is exactly the call this SC exists for — but a disagreement is only a
**failure** when the reordered content's meaning depends on sequence. CSS
repositioning (F1) is the classic culprit: content that reads correctly visually but
whose DOM order scrambles the meaning.

## 3. Decision procedure (walk in order)

1. **Does sequence affect meaning here?** Identify the content type:
   - Sequence-dependent: instructions/steps, a question followed by its options,
     narrative prose, a label preceding its field, numbered/ordered lists, dialogue,
     legend-then-data, "before/after". → SC applies.
   - Sequence-independent: sibling cards/tiles, nav vs. main, unordered link lists,
     a sidebar of unrelated widgets. → SC generally not engaged by reordering.
2. **Compare visual order (screenshot) to DOM order (`readingOrder`).**
   - Match → **pass**.
   - Mismatch AND the mismatch changes meaning (e.g. options serialize *before*
     their question; an answer reads before its prompt; a field's label lands after
     the field's later sibling) → **fail** (typically F1 / CSS-reposition or
     source-order defect).
   - Mismatch but content is sequence-independent, or an alternative order is still
     "correct" and coherent → **pass**.
3. **Survey/question probe:** if answer options serialize before the question stem,
   or a rating scale's endpoints read in an order that inverts the scale meaning →
   **fail**.
4. **Plain-text layout failures (F32/F33/F34):** whitespace used to fake columns or
   tables that linearize into gibberish → **fail**.
5. **Layout tables (F49):** if a layout table does not make sense when linearized →
   **fail**; if it linearizes coherently → pass.
6. **Ambiguous meaning-dependence** — cannot decide whether the order matters →
   **needs_human**.

**Confidence:** `high` when both screenshot and serialization are clear and the
content type is unambiguous; `low` when meaning-dependence is a judgment call →
route to `needs_human`.

## 4. Pass exemplars

- **Aligned order.** Screenshot shows "Question 3 … [ ] A [ ] B [ ] C"; the
  `readingOrder` serialization emits the question stem, then A, B, C in that order.
  PASS.
- **Sequence-independent grid.** A dashboard of six unrelated stat tiles; DOM order
  differs from a masonry visual layout. PASS — reordering tiles does not change
  meaning; multiple correct orders exist.
- **Multi-column article, correct source order.** Two visual columns via CSS; the
  serialization reads column-1-then-column-2 as a continuous narrative that makes
  sense. PASS (C27/C6 satisfied).
- **Third-party nuance.** A Monaco editor renders lines out of naive DOM order for
  virtualization, but the accessible text/value exposes the code in correct line
  order. PASS — programmatic sequence is correct despite unusual DOM.

## 5. Fail exemplars

- **Options before question (F1/source order).** `readingOrder` serializes the
  answer choices *before* the question text, though visually the question is on top.
  A screen-reader user hears choices with no prompt. FAIL, severity 4.
- **CSS-repositioned instruction.** Screenshot shows a warning "Do this *before*
  submitting" above the form; DOM order places it after the submit button. Meaning
  ("before") is lost in reading order. FAIL, severity 3–4.
- **Whitespace pseudo-table (F34).** A schedule built from spaces in a `<pre>`
  block; linearized it becomes unreadable run-on text. FAIL, severity 3.
- **Label after unrelated content.** A field's visible label is positioned by CSS
  to sit beside the input, but in DOM order it follows a *different* field, so the
  reading order pairs the wrong label with the wrong input. FAIL, severity 4.

Third-party-widget caution: a widget with an unconventional DOM is **not** a failure
if its exposed reading/accessible order still conveys the correct meaning. Fail only
when linearized meaning is actually wrong — not for DOM novelty.

## 6. needs_human triggers

- Whether the content's order carries meaning is genuinely ambiguous (e.g. a set of
  related-but-not-strictly-ordered panels).
- Visual and DOM order differ, but deciding if the DOM order is *a* correct
  alternative order needs domain/semantic understanding the probe can't supply.
- Content depends on a rendered visual relationship (arrows, connecting lines,
  spatial grouping) that the text serialization cannot represent — see limits.
- RTL/bidirectional or mixed-direction text where correct sequence needs language
  knowledge.

## 7. Known evidence limits

- `readingOrder` captures **text/roles**, not spatial/visual relationships conveyed
  purely by position (arrows, adjacency, color grouping) — those belong partly to
  1.3.1/1.3.3 but can confound the meaning call here.
- Dynamic reflow at other viewport widths isn't in a single serialization; a
  responsive reorder could pass at one width and fail at another. → request
  `readingOrderAtWidths`.
- CSS `order`/flex/grid reordering is only detectable via the screenshot↔DOM diff;
  if the screenshot is at a different breakpoint than the serialization, the diff is
  unreliable. → request `matchedViewportPair`.
- The probe does not run an actual screen reader; it uses DOM/aria order as a proxy
  for what AT announces (a strong but not perfect proxy).

## 8. Severity guidance

- **5** — reading order makes a required task impossible to understand
  non-visually (e.g. sequential instructions fully scrambled).
- **4** — meaning inverted or lost for a key interaction (options before question;
  wrong label-to-field pairing).
- **3** — meaning degraded but recoverable with effort (misplaced note, pseudo-table
  that is hard but not impossible to parse).
- **2** — minor order oddity with low meaning impact.
- **1** — cosmetic order difference in sequence-independent content.
